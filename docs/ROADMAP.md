# Практична дорожня карта

Виходимо з того, що React, TypeScript і веб тобі вже знайомі. На кожен блок: коротке пояснення → код → експеримент → пояснення результату своїми словами. Орієнтир: 1–3 сесії по 60–90 хв на блок; оцінювання й роботу з реальними записами плануємо окремо. Це навчальна оцінка обсягу, не дедлайн бакалаврської.

Аудіотерміни пояснюємо з нуля, одразу під абзацом, де вони вперше з’являються. Після кожного кроку пояснюємо, навіщо він потрібен тюнеру та що робитимемо далі. [Словничок у кінці першої лабораторної](LAB-01.md#словничок) залишається додатковою довідкою.

## Інструменти

Оновлення: базове визначення частоти, ноти й відхилення вже реалізоване. [Лабораторна 02](LAB-02.md) задає порядок розбору коду. Згладжування та дослідження точності на фізичних пристроях залишаються наступними кроками.

**Web Audio API** — вбудоване API браузера, а не стороння бібліотека. Воно дає аудіограф, семпли й генератори. **MediaDevices/getUserMedia** дає потік мікрофона. **Pitchy** — невелика бібліотека для оцінки основної частоти одного тону; її підключаємо в блоці 2. Вона повертає частоту й clarity, а не ноту чи акорд. Clarity — показник вираженості періодичності, не калібрована ймовірність правильності.

| Блок                     | Що пишемо й одразу бачимо                                               | Практичний експеримент                                             | Критерій завершення                                                                                                   |
| ------------------------ | ----------------------------------------------------------------------- | ------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------- |
| 1. Сигнал (реалізований) | Мікрофон, синусоїда, осцилограма, RMS/dBFS                              | Змінюємо окремо частоту й амплітуду                                | Пояснюєш семпл, sampleRate, розмір вікна й відрізняєш висоту звуку від рівня                                          |
| 2. Основна частота       | PitchDetector, findPitch, Hz і clarity поруч із хвилею                  | 220/440/880 Hz; потім тихий сигнал, шум і реальна струна           | Отримуємо виміряне значення; не показуємо ноту з шуму; пояснюєш періодичність                                         |
| 3. Музична нота          | Hz → MIDI-номер → назва й октава; A4 як параметр                        | 440 → A4, 880 → A5; міняємо еталон 440/442                         | Є тести граничних частот і невалідних значень; дані потрапляють у наявний дисплей                                     |
| 4. Тюнер                 | Центи, стрілка, допуск, згладжування, вибір струни                      | Розстроюємо гітару; порівнюємо стабільність і швидкість реакції    | Інтерфейс не стрибає безконтрольно й не приховує зміну тону; пороги обґрунтовані                                      |
| 5. Точність і швидкодія  | Стенд із відомими сигналами/записами, журнал метрик                     | Частота, рівень, шум, інструмент, розмір вікна, пристрій і браузер | Відтворювані перевірки: помилка в центах, octave errors, частка відмов, час обчислення; повну затримку міряємо окремо |
| 6. Акорди                | Окремий експеримент із поліфонією; базовий підхід і, за потреби, модель | Одна нота проти тризвуку, інверсії та різні тембри                 | Узгоджений набір акордів, ліцензовані дані, confusion matrix; чесно описані межі                                      |
| 7. Збереження            | API та БД для налаштувань/профілів/результатів тестів                   | Відновлюємо налаштування й переглядаємо історію                    | Аудіоаналіз залишається в браузері; бекенд має конкретну роль і перевірені помилки                                    |
| 8. Захист                | Архітектурна схема, порівняння, графіки, демонстраційний сценарій       | 5–7 хв пояснення + питання + сценарій відмови мікрофона            | Кожне твердження про якість підкріплене власними даними                                                               |

## Порядок технічних рішень

1. Починаємо з `AnalyserNode` і часових семплів. `fftSize` задає розмір вікна, навіть якщо FFT у цьому блоці не читаємо.
2. Вивчаємо Pitchy на контрольованій синусоїді, потім додаємо реальні записи. Не плутаємо FFT-пік з основною частотою складного музичного звуку.
3. Спершу робимо правильний простий варіант, потім вимірюємо вузькі місця. AudioWorklet/Worker додаємо за результатами вимірювань.
4. Розпізнавання акордів не є «кілька разів викликати Pitchy». Воно потребує окремого способу виділення ознак і класифікації; обсяг узгоджуємо перед реалізацією.
5. Після кожного блоку записуємо: гіпотеза, що змінили, на чому перевірили, що не працює. Це матеріал експериментального розділу роботи.
