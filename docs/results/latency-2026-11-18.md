# Tuner frame path: AnalyserNode vs AudioWorklet (2026-11-18)

Both paths use the same input, the same YIN detector (`ToneDetector`), the same
smoother, the same frame size (`tunerFrameSize`: 2048 samples at 48 kHz) and the
same nominal hop (`ANALYSIS_HOP_MS` = 75 ms). The only difference is how a frame
reaches the main thread:

- **AnalyserNode**: `requestAnimationFrame` polls `getFloatTimeDomainData` when
  at least 75 ms have passed since the last analysis.
- **AudioWorklet**: `FrameRing` in the worklet keeps the newest 2048 samples and
  posts a copy every 3600 samples (75 ms); the main thread analyses it on arrival.

The switch is on the Tuner and Note finder pages ("AnalyserNode / AudioWorklet",
saved in the settings). The line next to it shows the live numbers below.

## What is measured (`src/audio/latency.ts`)

| Name | From | To |
|---|---|---|
| wait | newest sample of the frame (AudioContext clock) | frame in main-thread JS |
| YIN | frame in JS | YIN + smoothing done |
| display | frame in JS | the next painted frame after React showed the result |
| total | wait + display | |
| interval | one analysed frame | the next one |

For AnalyserNode, *wait* is 0 by definition: the analyser is read on the spot
and its newest sample is the newest rendered one (at most one 128-sample render
quantum, 2.7 ms, old; this method cannot see less). For AudioWorklet, *wait* is
`AudioContext.currentTime` at arrival minus the time of the newest sample, so it
moves in steps of one render quantum (2.7 ms at 48 kHz).

## Results

Setup: production build (`vite build` + `vite preview`), headless Chrome 157 on
Windows 11 (desktop), 48 kHz, input = the page's test generator (OscillatorNode,
110 Hz sine) through the same graph as the microphone. Each run 20 s after a
1.5 s settling time; runs alternate between the paths. Times in ms.

| Path | Run | Frames | wait median / p95 | YIN median / p95 | display median / p95 | **total median / p95** | interval median / p95 |
|---|---|---|---|---|---|---|---|
| AnalyserNode | 1 | 240 | 0 / 0 | 1.9 / 2.8 | 17.5 / 18.7 | **17.5 / 18.7** | 83.3 / 83.7 |
| AnalyserNode | 2 | 240 | 0 / 0 | 2.1 / 3.5 | 17.6 / 19.7 | **17.6 / 19.7** | 83.3 / 84.1 |
| AudioWorklet | 1 | 267 | 5.3 / 8.0 | 1.7 / 2.9 | 12.9 / 19.0 | **15.2 / 22.0** | 72.3 / 84.1 |
| AudioWorklet | 2 | 267 | 2.7 / 8.0 | 1.6 / 2.6 | 9.2 / 19.8 | **15.3 / 25.1** | 72.2 / 84.5 |

An earlier run on the development server (React development mode, 12 s per run)
gave total median / p95 of 17.5 / 19.3 ms (AnalyserNode) and 22.2 / 31.1 ms
(AudioWorklet), so the order of the medians is not stable between runs.

## Reading the numbers

- YIN itself costs about 2 ms per frame on both paths.
- Most of the time is waiting for the screen. The AnalyserNode path analyses
  inside `requestAnimationFrame`, so the result is painted one display frame
  (16.7 ms at 60 Hz) later, every time: low spread. Worklet frames arrive at
  any moment relative to the display, so *display* is shorter on average but
  spreads more, and *wait* adds 3–8 ms.
- The real hop differs: AnalyserNode is polled on display frames, so 75 ms
  becomes 83.3 ms (5 display frames at 60 Hz, 12 analyses/s); the worklet keeps
  the audio clock (75 ms nominal, 13.3 analyses/s; the median gap is 72 ms
  because messages arrive in bursts).
- On this desktop the difference in total latency is a few milliseconds either
  way, far below what the display smoother adds. It does not settle which path
  is better on a phone.

## Not measured yet

- A real phone or tablet (slower main thread, other display rates, Safari).
  The live line on the Tuner page shows the same statistics there.
- A real microphone (the input latency of the device is the same for both paths
  and is not included here).
- Load on the main thread (e.g. the chord page or a busy page), where the
  worklet path is expected to keep its timing better than polling.
